# api-gateway

The api-gateway is the read path of the pipeline. It's a stateless HTTP service in front of ClickHouse that lists GPUs and serves one GPU's telemetry, ordered by time. It connects as the `api` user that the `telemetry-store` chart creates. That user is read-only and capped on execution time, memory, result rows, rows read and concurrent queries.

## Endpoints

| Endpoint | Returns |
| --- | --- |
| `GET /api/v1/gpus` | GPUs that have reported telemetry, from the `gpus` registry table (it never scans `telemetry`) |
| `GET /api/v1/gpus/{id}/telemetry` | The GPU's telemetry, ordered by time |
| `GET /api/v1/gpus/{id}/telemetry?start_time=...&end_time=...` | The same, within an inclusive time window; either bound may be left out |
| `GET /api/v1/swagger.json`, `GET /api/v1/swagger.yaml` | The Swagger 2.0 document, [openapi/swagger.json](openapi/swagger.json) and [swagger.yaml](openapi/swagger.yaml), generated by `make swagger` and embedded in the binary |
| `GET /api/v1/docs` | Swagger UI for that document, with "Try it out" against this gateway. Your browser loads the UI from jsDelivr; the pod needs no internet access |

`{id}` is the DCGM form `GPU-5fd4f087-86f3-7a43-b711-4771313afc50`, or the bare UUID. Responses always use the `GPU-` form. Times are RFC 3339 with optional fractional seconds, for example `2025-07-18T20:42:34Z` or `2025-07-18T20:42:34.5+05:30`. They are returned in UTC with nanoseconds.

Every query parameter is optional. The calls below send none beyond the time window, and the output is trimmed (`…`).

**Everything by default.** Both endpoints return every matching item unless the request sets the optional `limit`. With `limit`, telemetry returns the earliest `limit` entries and the GPU list returns the first `limit` GPUs. `truncated` is `true` only when a `limit` left items out; the gateway reads one row past the limit to know. There is no paging.

**Large results.** The `api` user may receive at most 100,000 rows per ClickHouse query, so the gateway reads results in chunks of `chunk_rows` (10,000), each resuming exactly after the previous chunk's last key `(ts, metric_name, streamer_id)`.
- If ClickHouse fails after the 200 has been sent, the gateway aborts the connection, so the client sees a broken transfer and never a body that looks complete. `gateway_stream_aborts_total` counts these.
- The GPU list is small, so it is built in memory and cached.

### Handling an interrupted stream (for API clients)

A telemetry response is streamed, so a failure after the first entry cannot change the 200 status; the gateway breaks the connection instead. A client should:
1. **Treat any broken transfer as a failure.** Go reports `io.ErrUnexpectedEOF`, Python `requests` raises `ChunkedEncodingError`, and curl exits with code 18. A complete document always ends with `"count":N,"truncated":…`; check that `count` equals the number of entries received. Never use a partial body.
2. **Resume, don't restart.** Pin `end_time` on the first request (for example, to now) so the result set is stable. On a failure, request again with `start_time` set to the timestamp of the last complete entry received. The bound is inclusive, so drop the entries already seen, keyed by `(timestamp, metric, streamer_id)`. Entries are ordered by that key, so this resumes exactly where the stream broke.
3. **Parse incrementally** (Go's `json.Decoder.Token`, Python's `ijson`), so the client also keeps memory bounded and always knows the last complete entry.
4. **Retry with exponential backoff and jitter**, honour `Retry-After` on a 429, and cap the attempts.
5. **For very large ranges, split the window** (for example, by hour), so each retry repeats less.

**Errors** are JSON: `{"error": "...", "request_id": "..."}`.

| Status | When |
| --- | --- |
| 400 | A bad id, time or limit; `start_time` after `end_time`; an unknown query parameter (so a typo such as `startTime` can't quietly return the whole history) |
| 404 | The GPU isn't in the registry. A known GPU with nothing in the window gets `200` with an empty list |
| 422 | The query hit the `api` user's rows-read or memory cap: narrow the window |
| 429 | No query slot became free within `queue_wait`, or ClickHouse's quota or concurrency cap was hit. Sent with `Retry-After: 1` |
| 503 / 504 | ClickHouse unreachable / the query timed out |

ClickHouse's error text is logged with the request id and never sent to the client.

## How a request is served

- **One shard per request.** Each query pins `gpu_uuid` to one constant value. In replicated mode the `api` profile sets `optimize_skip_unused_shards`, so the Distributed table reads only the shard the GPU hashes to. This was checked on the 2×2 dev cluster: all three query shapes run under `force_optimize_skip_unused_shards=1`, which makes ClickHouse refuse any query it can't route to specific shards.
- **Reads in sort order.** `WHERE gpu_uuid = ? AND ts BETWEEN ...` is a prefix of the table key `(gpu_uuid, ts, metric_name, streamer_id)`. `ORDER BY` follows that key, so ClickHouse reads in order and stops at each chunk's `LIMIT`. The chunks resume with keyset conditions on the same key. These are the query shapes that `clickhouse/tests/run.sh` pins.
- **No duplicates.** Delivery is at-least-once. A replayed row lingers until ClickHouse merges it away, and until then `LIMIT 1 BY` on the key hides it. The registry is read with `FINAL`.
- **Query slots.** Each pod runs at most `max_inflight` ClickHouse queries (4). Further requests wait up to `queue_wait` (1 s), then get 429. The `api` user may run 8 concurrent queries, which leaves room for the old and new pod to overlap during a rollout. When you add replicas, keep replicas × `max_inflight` within 8, so a burst is turned away by the gateway before ClickHouse starts rejecting queries.
- **GPU list cache.** Each `GET /gpus` response is cached for `gpu_cache_ttl` (5 s), per `limit`. The registry changes about once a minute per GPU.
- **Parameters, not SQL.** Every value taken from a request reaches ClickHouse as a typed server-side query parameter (`{gpu:UUID}`, `{start:Int64}`, ...).

**Timeouts and the locked `max_execution_time`.** clickhouse-go turns any context deadline over 1 s into a `max_execution_time` setting on the query. The `api` profile locks that setting, so ClickHouse would reject the query with code 452. The store hides the deadline from the driver but keeps the cancellation (`noDeadline` in [internal/store](internal/store/store.go)). ClickHouse's own 10 s cap therefore limits the query, and `query_timeout` (15 s) is a backstop for a hung connection. The integration tests use deadline contexts so this stays covered.

## Configuration

Every flag is also `GATEWAY_<NAME>`; flags win.

| Flag | Default | Notes |
| --- | --- | --- |
| `http_addr`, `admin_addr` | `:8080`, `:9090` | The API, and `/healthz` `/readyz` `/metrics` |
| `ch_addr` | `clickhouse-telemetry-store:9000` | ClickHouse native protocol |
| `ch_database`, `ch_user` | `default`, `api` | The read-only user from the `telemetry-store` chart |
| `ch_password` | | Set through `GATEWAY_CH_PASSWORD`; the chart reads `api-password` from the Secret `telemetry-store-credentials` |
| `ch_table`, `ch_gpus_table` | `telemetry`, `gpus` | |
| `max_inflight`, `queue_wait` | 4, 1s | Query slots per pod, and how long a request waits for one |
| `query_timeout` | 15s | Per query, so per chunk; a backstop, since ClickHouse stops a query at 10 s |
| `chunk_rows` | 10000 | Rows per ClickHouse query when reading a result in chunks; at most the `api` user's 100,000 result rows |
| `gpu_cache_ttl` | 5s | 0 disables the cache |
| `log_level` | `info` | |
| `drain_delay`, `shutdown_grace` | 5s, 20s | On SIGTERM: unready but still serving, then finish in-flight requests |

## Health and metrics

- `GET /healthz` is liveness. It never depends on ClickHouse, because restarting the gateway can't fix ClickHouse.
- `GET /readyz` returns 200 while ClickHouse answers pings, and 503 from SIGTERM onwards. Shutdown keeps serving for `drain_delay` while the Service drops the pod. The chart starts the new pod before stopping the old one, so even a single replica restarts without dropping requests.
- `GET /metrics`:

| Area | Metrics |
| --- | --- |
| HTTP | `gateway_requests_total{route,code}`, `gateway_request_duration_seconds{route}` (route is the matched pattern, never the raw path) |
| ClickHouse | `gateway_query_duration_seconds`, `gateway_query_errors_total`, `gateway_inflight_queries`, `gateway_clickhouse_up` |
| Protection | `gateway_rejected_total` (429 from the query slots only; quota 429s show in `gateway_requests_total{code="429"}`), `gateway_stream_aborts_total`, `gateway_gpu_cache_hits_total`, `gateway_gpu_cache_misses_total` |
| State | `gateway_ready` |

## Build, test, deploy

From the repo root:

```bash
make test                                # handler, main and metrics tests against an in-memory store
make coverage                            # with the store's ClickHouse tests in Docker: 90.6 % for the gateway
bash api-gateway/tests/clickhouse-test.sh # store tests against a throwaway ClickHouse in Docker (pinned image, dev users, chart migrations)
make docker SERVICE=api-gateway          # build context api-gateway/, loaded into minikube
make deploy SERVICE=api-gateway          # namespace telemetry; needs the telemetry-store release
curl -s http://$(minikube ip):30080/api/v1/gpus   # the dev NodePort; Swagger UI at /api/v1/docs
make api-port                            # the same on http://localhost:8080, in the background (make api-port-stop ends it)
```

The ClickHouse tests cover:
- inclusive bounds at nanosecond precision;
- unmerged duplicates hidden;
- chunked reads that match a single read exactly, across chunk boundaries with duplicates on both sides and a metric name containing a quote;
- a row cap applied after duplicates are removed, returning the earliest entries;
- registry duplicates collapsed;
- queries carrying deadlines;
- the `api` user being unable to insert.

**The Swagger file is generated with [swag](https://github.com/swaggo/swag) (v1.16.6, pinned in the Makefile), never edited.** `make swagger` reads the annotations and writes [openapi/swagger.json](openapi/swagger.json) and [swagger.yaml](openapi/swagger.yaml). The annotations live in three places:
- The general API information (`@title`, `@description`, …) is above `main()` in [cmd/api-gateway/main.go](cmd/api-gateway/main.go).
- Each endpoint's `@Summary`, `@Param`, `@Success`, `@Failure`, `@Header` and `@Router` are above its handler in [internal/api/api.go](internal/api/api.go).
- The response schemas come from the Go response structs. A field's comment is its description, a `@name` comment sets the schema name, and the `format`, `example` and `validate:"required"` tags fill in the rest.

To change the API, update the code and its annotations together, then run `make swagger` and commit the result. Three checks catch a mismatch:
- `make test` (`openapi_test.go`) fails when the documented paths, query parameters or response fields don't match what the code serves, accepts and encodes. Annotations are comments, and the compiler doesn't check them.
- `make swagger-check`, part of `make ci`, fails while the committed files differ from what swag generates now.
- No parameter has a `default` or `example`, so Swagger UI's "Try it out" sends only what you type. A test keeps it that way.

The output is Swagger 2.0 (OpenAPI 2.0), which is what stable swag produces. To lint it, run `npx @redocly/cli@1.25.0 lint api-gateway/openapi/swagger.json --extends=minimal`.

The chart (`helm/api-gateway`) runs 1 replica, which is enough for light traffic. With `replicas` above 1 it adds a PodDisruptionBudget and spreads the pods across nodes. It has a NetworkPolicy: the API port is open to every source by default (narrow `networkPolicy.api.from` to the ingress controller in prod), metrics are open to the `monitoring` namespace, and egress goes only to DNS and ClickHouse. There is also an optional Ingress (`ingress.enabled`) that routes only `/api/`.
